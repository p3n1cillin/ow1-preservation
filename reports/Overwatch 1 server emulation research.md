# Public sources point the HUD at mode 0x18

Research recovered from Claude branch d8b2998. This report predates runs 252 onward;
see [HANDOFF.md](../HANDOFF.md) for later validation and corrections. Run 250 was
a subgraph scheduling failure fixed in 252. The current private responder already
sends component-51 health through HeroHealth.


The single most actionable public lead for this project is not a Blizzard talk but the code comments of the other 1.74.0.0.104319 server line (Boi-027's fork of the vanished squeeeezy "overwatch-1.74-lobby-server"). They say the Practice Range runs game mode **0x0230000000000018**, whose per-team controller graph **0x13C1** starts the hero-HUD graph **0x20E4** as a server-created sub-instance, alongside a separate game-mode entity, explicit filter bits, possession components 44/75/123 and a one-part health component 51. This project instead runs mode **0x023000000000005A** with graphs 0x13C0/0x0C8E/0x0C90 and has proven that hero HUD graph 0x01CF stalls waiting for game message 0x1291, which only 0x20E4 sends. Blizzard's own material, chiefly Dan Reed's GDC 2017 Statescript slides and Tim Ford's GDC 2017 netcode talk (read through a Chinese translation), does not document any wire format. What it does supply is the governing rules: Statescript is server-authoritative, only one entity per client is "local" and predicted, client-only subgraphs run only while their replicated owning state is active, health and filter components are never predicted or rolled back, and remote entities are rendered by interpolating server MovementState. OWLib's OW1-branch STU types supply the authored-data side: team controller/body scripts, child-entity hardpoints, presentation entities for gallery and showcase, and the WPF-like UX binding model. On the wire format itself, this project's reverse engineering is ahead of every public source. Its AES-GCM envelope, reliable channels, statescript tag decoding and one-bit/two-bit StDt table are matched only by the unverified fork. That fork's claims, which come with no public evidence and an unclear license, must therefore be checked against the original client before anything is built on them.

## Three tiers of sources, and only one covers 1.74 gameplay

The public record splits cleanly into three tiers. The first tier is primary Blizzard material. Reed's 82-page slide deck is the only official document read in full. It defines StatescriptDeltas, per-client ghosts, Local/Remote packets, SYNC_ALL remote-sync compilation and the node catalogue ([Reed slides](https://media.gdcvault.com/gdc2017/Presentations/Reed_Dan_NetworkingScriptedWeapons.pdf)). Ford's talk is free on GDC Vault, but no English transcript was reachable. Its details (16 ms command frames, 15.2 ms time dilation, sliding input windows, backward reconciliation) therefore come from the kevinan Chinese translation, cross-checked against Edgegap's independent English summary ([max2d.com translation](https://max2d.com/archives/956); [Edgegap, secondary](https://edgegap.com/blog/game-backend-deep-dive-overwatch-2016-netcode-architecture-rollback)). Reed's spoken narration and Q&A are likewise known only through a Chinese write-up ([lfzxb translation](https://www.lfzxb.top/ow-gdc-weapon-and-skillsystem/)). Philip Orwig's replay talk survives publicly only as an abstract ([GDC Vault 1024053](https://gdcvault.com/play/1024053/Replay-Technology-in-Overwatch-Kill)). Patch notes and the Workshop wiki add per-player HUD toggles.

The second tier is community reverse engineering with clear provenance. OWLib's `ow1` branch (head 243caa9) gives retail field and instance hashes, but its generated STU types date from a January 2022 regeneration, not from 104319. Hashes are stable identifiers; offsets are hints ([OWLib ow1 types](https://github.com/overtools/OWLib/tree/243caa939efacc28eab7af8e8944f89f123b586b/TankLib/STU/Types)). Prometheus targets the 0.8 beta (build 24919) and is an in-client DLL that writes entities directly, not a server. It is AGPL and is this project's upstream, so code reuse is license-compatible. Its offsets and component numbers, however, are beta-only ([saturn-xvi/prometheus](https://github.com/saturn-xvi/prometheus)). The owdev wiki and the 39C3 talk subtitles add 0.8 ECS tables and Statescript entry semantics ([owdev ECS](https://owdev.wiki/wiki/index.php/Game/ECS); [39C3 subtitles](https://static.media.ccc.de/media/congress/2025/1266-d08f6f41-a731-57f7-ba40-8f38464f2dcd-eng.vtt)).

The third tier is the 1.74 community line, which needs care. Boi-027's lobby research is MIT-licensed and on indefinite hiatus since September 2026. It documents the PANAMA JAM cipher, the HMAC key schedule and Arxan/ACG limits ([Boi-027 research](https://github.com/Boi-027/Overwatch-1-v1.74-Lobby-Research)). The game-server code lives in "overwatch-1.74-lobby-server". The forks carry an MIT notice, but the original squeeeezy repository returns 404, so the author's grant cannot be confirmed at the source. The upstream research repos also publish client-embedded keys and resource keys. Its game-server claims are code comments and a WIP note crediting non-public "ProCore" live tests and "Xref" OW2 traffic captures, with no video or independent verification ([Boi-027 fork](https://github.com/Boi-027/overwatch-1.74-lobby-server); [squeeeezy original, 404](https://github.com/squeeeezy/overwatch-1.74-lobby-server)). Under this project's rules it is **reference-only**: never import its code or bundled keys/credentials, and re-derive every claim from the original client, dumps or authored data. Plasmawatch (Go Battle.net emulator for 0.8/1.65) is archived and ships a private key, and it carries nothing at the game-server level ([Plasmawatch](https://github.com/plasmawatch)).

The table makes the asymmetry plain. On transport and replication framing, the fork independently agrees with what this project already verified, and Blizzard is silent. The fork adds new information only on gameplay semantics: which mode, which graphs, which components. Those are exactly the parts it says are still broken for itself.

## Hero HUD: the 0x1291 sender belongs to a mode this project never ran

The project's own trace is precise. Tracer graph 0x4B runs hero-HUD graph 0x01CF on the hero. 0x01CF passes its 0x0717 gate, then node #101 waits for game message 0x1291. That message is sent only by graph 0x20E4's client-only sender #187. Run 249 put 0x0C90 on the controller and reached #187, but 0x1291 never reached the hero. Run 250 put 0x0C90 on the hero and broke hero frames. Public sources explain why both attempts are structurally suspect.

Authored data first. OWLib names `STUGameModeTeam.m_controllerScript` (field 0xA2781AA4) and `m_bodyScript` (0x76E8C82A), and `STUGameMode` field 0xCF63B633 as the game-mode script ([OWLib types](https://github.com/overtools/OWLib/tree/243caa939efacc28eab7af8e8944f89f123b586b/TankLib/STU/Types)). The project's earlier deep-reference scan found that mode 0x5A references 0x13C0 via cf63b633, 0x0C8E via 76e8c82a and 0x0C90 via a2781aa4. By OWLib's names, **0x0C90 is mode 0x5A's per-team controller script, 0x0C8E its body script, and 0x13C0 the mode script**. That supports 0x0C90 on the controller (where run 249 got #187 to execute) and argues against moving it to the hero. It also makes 0x0C8E a hero-body graph, not a controller graph. This is an inference from field names, but the hashes are exact.

The fork then supplies the missing branch. Its `heroselect.py` says each team of a game mode names its controller graph. For the Practice Range that graph is **0x13C1**: "its SubScript states start the HUD (state 42 -> graph 20E4) and hero select (state 43 -> 288A, whose state 0 -> 288B)". It adds that the PvP modes use 0x0C90, "whose HUD graph is client-only, so the client makes that one itself" ([Boi-027 fork](https://github.com/Boi-027/overwatch-1.74-lobby-server)). Its owner frame puts 0x13C1 on the player (controller) entity as instance 1 with owner-state bits 25, 37 and 36. Bit 36 creates 0x20E4 as instance 4 with parent (1, state 42). The fork's map data lists both 0x0230000000000018 and 0x023000000000005A as Practice Range modes with the same four placeables. Read against this project's findings, **mode 0x5A looks like the PvP-style team setup (controller 0x0C90), while the fork's mode 0x18 uses a Practice-specific controller that hosts 0x20E4 as a replicated sub-instance**. The fork's "36 vs 42" numbering is consistent with its other claim that owner-frame state lists omit client-only and server-only states. That is an inference worth checking, because this project's emulation found that its full snapshots index all `m_states`, and the fork's `HERO_SELECT = Graph(0x288B, 30, 4)` disagrees with this project's emulator-verified (32 sync vars, 146 states). One of the two describes a different frame form, and that must be settled before any 0x13C1 frame is encoded.

Reed's rules explain why hosting matters. Client-only subgraphs are "fully simulated whenever their owning State is active", and remote entities otherwise do not simulate instances ([lfzxb translation](https://www.lfzxb.top/ow-gdc-weapon-and-skillsystem/); [Reed slides](https://media.gdcvault.com/gdc2017/Presentations/Reed_Dan_NetworkingScriptedWeapons.pdf)). The fork states the same from experiment: "Instances the server makes never run their own Entry nodes (only client-only ones run), so the server sends what those would have done". That matches this project's run 225, where 0x041A on the controller ran no nodes. A client-only sender inside a server-created 0x20E4, whose parent state is replicated as active, is exactly the shape that should run #187 on the client.

Run 249 shows the second half of the problem: #187 ran, but the message did not arrive. OWLib's retail types show that delivery is scoped by the sender's `m_targets` (on `STUStatescriptActionSendGameMessage`) and the receiving entry's `m_filter`, not by a channel ([OWLib types](https://github.com/overtools/OWLib/tree/develop/TankLib/STU/Types)). The project already knows #187's target #193 is STU_1D719351, probably "own entity". If the target resolves through the controller's possession data to the body, a missing possession link would explain the miss. The fork's possession model is more complete than the project's. Component 44 is MECPossessorData (current, view target, primary possessable = body ×3). **Component 75 is MECCharacterController** (current hero, skin theme, ..., last valid hero) on the player. **Component 123 is MECCharacterBody** (hero GUID) on the body. This project sends only component 44. This inference is testable offline by evaluating #193's config var against a dump.

Three further public facts constrain the remaining search. First, the Workshop's "Disable Hero HUD" disables the HUD "for one or more Players until reenabled", which implies the hero HUD is on by default, so there is no "enable HUD" message to find ([workshop.codes](https://workshop.codes/wiki/articles/disable+hero+hud); [PTR notes 15 Jul 2020](https://eu.forums.blizzard.com/en/overwatch/t/overwatch-ptr-patch-notes-%E2%80%93-july-15-2020/23790)). That agrees with the project's finding that HUD_Root's `ShowHeroHud` (var 0x34F5) defaults true. Second, the fork reports that the spectator filter bit **0x10000000** caused "the spectator's HUD panel". The replay viewer's "First-Person Hero HUD" option and the client strings `Spectator_Show1PHeroHUD` show that a spectator-like context routes the HUD differently ([PTR notes 19 Nov 2020](https://eu.forums.blizzard.com/en/overwatch/t/overwatch-ptr-patch-notes-%E2%80%93-november-19-2020/24881)). Third, OWLib shows the UX layer is WPF-like. A UXScreen (type 0x5A, which is what the project's 0x09A0 "layers" decode to) has a root element, Bindings with PropertyPaths, `m_fallbackValue`, `m_sampleData` and `m_loadBehavior`. Presenters carry a condition (`m_3DBF6FD2`) and identifier-to-ConfigVar bound properties (`m_4FF3A882`) ([STUStatescriptStateUXPresenter.cs](https://github.com/overtools/OWLib/blob/243caa939efacc28eab7af8e8944f89f123b586b/TankLib/STU/Types/STUStatescriptStateUXPresenter.cs); [STUUXScreen.cs](https://github.com/overtools/OWLib/blob/243caa939efacc28eab7af8e8944f89f123b586b/TankLib/STU/Types/STUUXScreen.cs); [STUUXBinding.cs](https://github.com/overtools/OWLib/blob/243caa939efacc28eab7af8e8944f89f123b586b/TankLib/STU/Types/STUUXBinding.cs)). A screen whose data context (local hero, health part, weapon) is null can load, run its presenters and still draw nothing. That fits the project's long-standing "presenters run, widgets exist, nothing drawn" observation once 0x1291 is solved.

Prometheus adds 0.8-era statescript variables that a HUD could read. Every tick, its artpop2 branch writes current/max health floats to entity vars **0x06C4/0x06C9** and BYTE 1 to **0x094C**, commented "When this is 1 the statescript component does not add the 'spectator' graph" ([artpop2 entity_admin.cpp](https://raw.githubusercontent.com/saturn-xvi/prometheus/artpop2/Prometheus-Core/entity_admin.cpp)). Whether these IDs survived to 1.74 is unverified. They are cheap to grep in the project's decoded graphs. The fork itself is a sobering caveat: its WIP lists "Weapons, abilities and the in-game HUD" as not done. The mode-0x18 path is therefore the best *untested* lead, not a known solution.

## Remote entities, teams and health follow Ford's three-component rule

Ford's talk gives the cleanest public model for problem 6. `CombatUtilityIsHostile(a, b)` reads three optional components: filter bits (holding the team index), pet master and pet. "Two entities without filter bits... are not hostile", and a projectile's hostility traces back to its shooter. An entity can be hit only if it is hostile and has a `ModifyHealthQueue`. "Damage is never predicted on the client", and health bars wait for the server ([max2d.com translation](https://max2d.com/archives/956)). Reed adds that health and filtering components are excluded from rollback history ([Reed slides](https://media.gdcvault.com/gdc2017/Presentations/Reed_Dan_NetworkingScriptedWeapons.pdf)). Together these say that **team, hostility and health are plain server-replicated component state**. None of them is Statescript, and the client cannot fake any of them. The project's bots currently die by a server-side ray estimate. Unless they carry filter bits and the player carries a team, the client's own hostility logic will never treat them as enemies. That would account for missing hit markers, enemy outlines and damage feedback, independent of the HUD.

The fork's component layer gives concrete 1.74 values to verify. Component 26 is `MFilterBitsComponentData`; `0x800000 << team` selects the team's physics proxy. The client's own session builder gives its player `0x10040001 | team bit`, but 0x10000000 is the spectator bit, and "bodies with only it had no collision and no enemy outline". So the fork sends the player `0x00040001 | team bit` and the body the team bit only. Component 51 carries health: "16 health, 16 armour, 16 shield parts {u32 on, f32 now, f32 max, 4 bytes, 4×u8}", sent as one part `<IffII` (1, now, max, 1, 1) "as the HUD bar reads it" ([Boi-027 fork](https://github.com/Boi-027/overwatch-1.74-lobby-server)). Prometheus's 0.8 code uses a different team encoding (`0x40000 << team` in mask 0x3C0000, then 0x800000), and its spawner overwrites the team bits before finalising. Treat the beta numbers as historical and the fork's as claims to verify against the 1.74 hostility/spectator predicates ([entity_admin.h](https://github.com/saturn-xvi/prometheus/blob/main/prometheus/entity_admin.h)). The project's component-74 field 2 is a participant team value. The fork's component-74 map (`MECGameModeParticipant`: portrait, s16, slot, ..., "can select a hero") corroborates the project's own field-6 spawn-room finding. Filter bits, however, live elsewhere.

For movement, Ford says remote entities with MovementState are repositioned by interpolating between the last two received states, whatever they are: "moving platform, turret, door or Pharah". Server rewind for hit validation uses the same history, culled by a half-second bounding volume ([max2d.com translation](https://max2d.com/archives/956)). Blizzard's 2016 high-bandwidth change raised server-to-client updates from 21 to 63 per second, cutting interpolation delay from about 60 ms to about 20 ms ([Ten Ton Hammer](https://www.tentonhammer.com/news/overwatch-high-bandwidth-servers-rolling-out.amp); [GamesBeat](https://gamesbeat.com/overwatch-netcode-tick-rate-60hz/)). The fork turns this into a recipe. A remote body is placed by its create transform, then moved by one ch3 movement record per other body **every frame, "standing or not"**. Putting a movement state in the create leaves it at frame 0xFFFFFFFE, so the client refuses every later record that is not newer. The client keeps a movement state only when its command frame is newer than the newest it has. That is a precise, falsifiable explanation for the project's "isolated snapshots don't place non-controlled entities" and "remote entities don't fall". Remote entities never simulate; they only interpolate a continuous, monotonically framed stream. Kill feed and damage numbers have no public format. The project's own channel-3 27500 family (three entity IDs plus u64s, appended to world+0x138) remains the best candidate carrier. Ford's deferred "Contact" and ModifyHealthQueue singletons are the conceptual counterpart.

## Blink, Recall and muzzle origin need client-side machinery, not better teleports

Reed's node catalogue names the machinery that Tracer's kit is built from: **Blink Effect, Teleport, Find Ground, Track Validated Position, History Builder, History Rewinder, Teleport Over Duration and Suppress Movement Prediction** ([Reed slides](https://media.gdcvault.com/gdc2017/Presentations/Reed_Dan_NetworkingScriptedWeapons.pdf)). Reed's narration states that replication "does not follow links", and that SetVar and MovementMod actions are not replicated, because MovementMod "does its own replication" ([lfzxb translation](https://www.lfzxb.top/ow-gdc-weapon-and-skillsystem/)). Ford says abilities are predicted exactly like movement. The client rolls back to the last validated snapshot and replays buffered input; Overwatch predicts by default and opts out per ability ([max2d.com translation](https://max2d.com/archives/956)). The retail Blink is therefore a client-predicted state in the hero's own synchronized instance. Its collision-safe destination comes from the same deterministic movement code on both ends. Positions and poses of all entities are kept historically, which is the natural source for Recall.

The project's server teleports fail on two counts that public sources make explicit. The destination is never collision-resolved. The fork concedes the same structural gap: "the client... never tells the server where it is. The server moves a copy from the commands" with a FlatMover that has no collision ([Boi-027 fork](https://github.com/Boi-027/overwatch-1.74-lobby-server)). The authoritative state is also not anchored to a command frame. Ford's reconciliation replays buffered inputs on top of the server state, so a snapshot treated as "now" picks up extra displacement from inputs replayed after it. The project's four repeated snapshots compound this. These two failure modes are an inference, but they follow directly from the published rollback model. Recall computed on the server is worse than Blink, because the server only knows a dead-reckoned position, while the client holds the true history. The right long-term direction is to activate Tracer's own Blink/Recall states at the pressing command frame and let client prediction do the movement. The project's run-160 crash happened before Codex corrected the StDt one-bit/two-bit table in runs 204 to 212. An emulator STOP after BlinkEffect entry is not proof of a client fault, so that experiment deserves a re-run offline. The fork's `owner_ack` note is relevant too: an ack-only owner delta every 0.1 s advances CmFD, "else it replays old key presses". Any predicted ability depends on the server advancing the acknowledged frame. As an interim, the fork's map data gives the authored Practice spawn for team 0 at (54.565, 1.000, 42.148), yaw −170.3, placeable 564. It can replace hand-found coordinates. Its y=1.0 differs from the project's measured y=2.0 render position, so check whether one is feet and the other a render origin before switching.

Projectile and tracer origin (problem 4) is an asset-graph problem that OWLib documents well. `STUEntityDefinition.m_childEntityData` (0xF29E4995) is an inline array of `STUChildEntityDefinition`. Each entry holds `m_child` (definition), `m_hardPoint` (type-0x3C hardpoint), identifier `m_49F782CE` and a flag byte `m_2263EA37`. Hardpoints resolve against the parent model's `STUModel.m_hardPoints[]`, which carries hardpoint GUID, parent bone, rotation and position ([STUEntityDefinition.cs](https://github.com/overtools/OWLib/blob/243caa939efacc28eab7af8e8944f89f123b586b/TankLib/STU/Types/STUEntityDefinition.cs); [STUChildEntityDefinition.cs](https://github.com/overtools/OWLib/blob/243caa939efacc28eab7af8e8944f89f123b586b/TankLib/STU/Types/STUChildEntityDefinition.cs); [OverwatchModel.cs](https://github.com/overtools/OWLib/blob/243caa939efacc28eab7af8e8944f89f123b586b/TankLib/ExportFormats/OverwatchModel.cs)). `STUFirstPersonComponent.m_entity` names a separate first-person entity definition ([STUWeaponComponent and types](https://github.com/overtools/OWLib/tree/243caa939efacc28eab7af8e8944f89f123b586b/TankLib/STU/Types)). The project's own graph dump shows Tracer children 0x169 and two 0x17 entries, which nothing creates today. The owdev wiki says entity prefix 0x60000000 is "used when a projectile is spawned on the client using a LeaseBlock" and that clients may only spawn 0x80000000-prefixed entities ([owdev ECS](https://owdev.wiki/wiki/index.php/Game/ECS)). Prometheus attributes D.Va floating to "the Mecha isn't spawned" and links children through a Backref component ([Prometheus README](https://github.com/saturn-xvi/prometheus)). Public sources do not say whether the 1.74 client instantiates `m_childEntityData` itself or expects server creates with a parent link. The fork's create flags have no parent field. A dump census, therefore, comes before any packet guess.

## Hero-select preview and gallery are client-run presentation data

Reed lists "Menus, Hero Gallery, End-of-match flow, Music" as **unsynchronized** scripts that only read variables off synchronized instances and receive their messages ([Reed slides](https://media.gdcvault.com/gdc2017/Presentations/Reed_Dan_NetworkingScriptedWeapons.pdf)). No Statescript replication will populate the gallery; its inputs are lobby data and resident assets. OWLib's DataTool names the five STUHero presentation entities: `m_gameplayEntity` "Gameplay3P", `m_previewEmoteEntity` "PreviewEmote", `m_322C521A` "Showcase", `m_26D71549` "HeroGallery" and `m_8125713E` "HighlightIntro". Preview weapons, with loadout, rotation and offset, sit in `m_previewWeaponEntities` and `m_C2FE396F` ([SkinTheme.cs](https://github.com/overtools/OWLib/blob/243caa939efacc28eab7af8e8944f89f123b586b/DataTool/SaveLogic/Unlock/SkinTheme.cs); [STUHero.cs](https://github.com/overtools/OWLib/blob/243caa939efacc28eab7af8e8944f89f123b586b/TankLib/STU/Types/STUHero.cs)). These match exactly the record references the project already found (03d0, 09fc, 0dda, 1438). Skins are pure GUID substitution through `STUSkinBase.m_runtimeOverrides`. The default unlock set is `m_heroProgression.m_7846C401[*].m_unlocks`, which DataTool exports as the "Default" event ([ExtractHeroUnlocks.cs](https://github.com/overtools/OWLib/blob/243caa939efacc28eab7af8e8944f89f123b586b/DataTool/ToolLogic/Extract/ExtractHeroUnlocks.cs)). Gallery "0/0" counts most plausibly come from the client intersecting those lists with owned unlock records (type 0xA5, raw 0x0250). That is inference, and run 203's "real default unlocks" may have differed in GUID set or record shape. The fork implements 24900 loadout slots, 24500 equip and a retail config key **0x87053C32** in lobby 36600 that "can put any loaded hero record in the menu" ([Boi-027 fork](https://github.com/Boi-027/overwatch-1.74-lobby-server)). That last claim offers a cheap discriminator. If a menu hero renders, the presentation-entity pipeline works, and the hero-select gap is about which state (OWLib's `STU_BB7F6C27`, with `m_hero` and `m_skin` config vars, is a candidate) or variable feeds the preview. No public source shows a working 1.74 hero-select 3D preview.

## Early instance failure: public sources are silent

No public source describes the instance join, its retry budget, timeout values or why a client would exit. Blizzard's LC-202 and the forum descriptions characterise failed game-server connections as UI-level disconnects, not process exits ([Blizzard Support 34859](https://us.support.blizzard.com/en/article/34859)). The fork offers three transport facts. The client sends SYN until it sees SYN|ACK. The transport "resends nothing". On the lobby side, the client dropped connections when neither the dialled address nor the real port matched. This project's failures (at least runs 124, 128, 134, 142, 184, 186, 188 and 210) show identical first exchanges and recur with configurations identical to successful neighbours (124 between 123 and 125). Exit code 1 with no dump and no LC-style UI points to a handled fatal path, not the 21801/21802 abort the project traced for missing definitions. The nondeterminism points at per-run random inputs (referral keys, connection id, salt), at timing races between responder bind, referral and first SYN, or at responder exceptions. The handoff already warns that responder crashes have masqueraded as client aborts (`-udp.err`). All of these are hypotheses; none has public backing.

## Conclusion

Public material changes the project's model of the HUD problem from "find the missing UI message" to "run the right game mode's team graphs on the right entities". The authored-data hashes in OWLib independently confirm that 0x0C90 is a controller script and 0x0C8E a body script. The 1.74 fork names a different Practice mode (0x18) whose controller graph hosts 0x20E4, the only sender of the message 0x01CF waits for. That claim is cheap to verify offline, and if it holds, it explains why every attempt to relocate 0x0C90 or 0x0C8E failed. Its value does not depend on trusting the fork's code. A second, independent thread runs through Ford, Reed and the fork alike: team, hostility, health and remote motion are ordinary replicated component state that the client never predicts. Filter bits, component 51 and a continuous movement stream are therefore prerequisites for combat feedback and plausibly for the HUD's data context. Neither is a cosmetic extra.

The limits are just as clear. No public source documents the 1.74 wire format beyond what this project has already verified. No public project has shown a working 1.74 hero HUD, server-run ability graphs, weapon child entities or a hero-select preview. Nothing public explains the early instance exits. The fork's remaining claims are unaudited, rest on non-public tests, and come from a repository whose original has vanished. They should be treated as hypotheses to falsify on the original client, never as code or data to import.
