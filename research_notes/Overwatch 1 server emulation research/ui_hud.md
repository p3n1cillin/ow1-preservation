# Overwatch UI/HUD architecture and hero-HUD show conditions (public knowledge, mapped to the OW1 preservation server)

Scope note: Blizzard has published very little about Overwatch's UI tech. The most useful public sources were (a) OWLib/TankLib's generated structured-data (STU) type definitions, (b) Workshop and patch-note wording that exposes per-player HUD toggles, (c) the Prometheus beta emulator source, and (d) GDC session abstracts. Everything under "Inferences" is reasoning, not a stated fact.

OWLib commits used: OW1-era type dump `243caa939efacc28eab7af8e8944f89f123b586b` (2022-10-21, "sync formats"; last OW1-era sync) and current HEAD `546efa19516d7df7ba138802d221c73ad886df28` (2026-10-11). Both were cloned read-only into a scratchpad, not into the project.

## 1. Blizzard talks/articles on Overwatch UI and the engine's UI tech

### Takeaway
I found no public Blizzard talk, blog or article on Overwatch's in-engine UI framework or hero-HUD logic. The relevant public talks cover Statescript networking (Dan Reed), ECS/netcode (Tim Ford) and replay/kill cam (Philip Orwig), all GDC 2017. Their abstracts confirm that Statescript drives high-level gameplay state and that the client was refactored for an interruptible kill cam. Slides and videos are behind the GDC Vault login and were not read.

### Cited Findings
- GDC 2017, Dan Reed, "Networking Scripted Weapons and Abilities in Overwatch". Statescript is Blizzard's proprietary visual scripting language for high-level state machines (hero weapons and abilities). The talk covers automated prediction and replication of script behaviour, and designers building heroes "with little or no new code" — [GDC Vault](https://gdcvault.com/play/1024041/Networking-Scripted-Weapons-and-Abilities); [Game Developer preview](https://www.gamedeveloper.com/design/attend-gdc-and-see-how-blizzard-scripts-i-overwatch-i-s-weapons-and-powers)
- GDC 2017, Timothy Ford, "Overwatch Gameplay Architecture and Netcode". Overwatch uses an Entity Component System (ECS) architecture — [GDC Vault](https://gdcvault.com/play/1024001/-Overwatch-Gameplay-Architecture-and). A third-party summary says it covers singleton components for shared state and about 46 systems / 103 component types on the client (unverified against the talk) — [glasp summary](https://glasp.co/youtube/W3aieHjyNvw)
- Ford's team wrote "the game simulation, animation, and user interface", so UI belongs to the same gameplay-engineering group as ECS/netcode — [Inven Global interview](https://www.invenglobal.com/articles/4865/interview-with-overwatch-dev-tim-ford-regarding-symmetra-turning-into-a-defense-hero-and-the-channel-system)
- GDC 2017, Philip Orwig, "Replay Technology in Overwatch: Kill Cam, Gameplay, and Highlights". It covers building replays in parallel with the network model, transferring reels within a hard respawn deadline, and "refactoring the game client architecture to support an interruptible kill cam" — [GDC Vault](https://gdcvault.com/play/1024053/Replay-Technology-in-Overwatch-Kill)
- GDC "The Data Building Pipeline of Overwatch" concerns content building and data conversion, not the UI runtime — [GDC Vault](https://gdcvault.com/play/1024019/The-Data-Building-Pipeline-of)
- 39C3 (2025) talk "Prometheus: reverse engineering Overwatch" (speaker breakingbread, using the 0.8.0.0 beta). It describes a "deterministic graph based scripting engine which handles (almost) everything which happens ingame", the ECS and building a server from scratch. The abstract does not mention UI/HUD — [CCC hub](https://events.ccc.de/congress/2025/hub/en/event/detail/prometheus-reverse-engineering-overwatch)
- The Prometheus README states Statescript controls "most in-game abilities, nearly all UI interactions, login logic, music, the lobby map, and in-game UI elements" — [saturn-xvi/prometheus README](https://github.com/saturn-xvi/prometheus)
- Job postings for Overwatch UI/UX artists describe scope "from the intro screen to the in-game HUD" with UI screens, transitions and VFX. They give no tech detail — [Hitmarker listing](https://hitmarker.net/jobs/blizzard-entertainment-ui-ux-artist-overwatch-2645436)

### Inferences
- Because UI is Statescript-driven (Prometheus README) and Statescript replication is automated (Reed abstract), the hero HUD is almost certainly shown by Statescript UX presenter states. Those states read replicated/synced variables and native component state. No dedicated "show HUD" network message is involved. This matches the project's finding that HUD_Root is loaded by a statescript node with bound properties `ShowHeroHud` / `ShowDistortion`.
- The kill cam refactor (Orwig) suggests the client can show the HUD for a non-live "world" (replay/kill cam). That fits the project's observation that the highlight/replay viewer graph also displays HUD_Root. The HUD is then probably parameterised by a "viewed/spectated entity" context rather than hard-wired to the live local player.

### Gaps
- No slides or transcripts were accessible for the Reed, Ford or Orwig talks (GDC Vault login). Whether they show UI-specific slides (e.g. the HUD as an ECS system, or the kill-cam second world) is unknown.
- No public ArtStation, blog or interview material about Overwatch HUD implementation was found. Searches returned only job listings.

## 2. Game states that show/hide the HUD; spectator/replay HUD options

### Takeaway
Public patch notes show the HUD split into independently toggleable groups. The spectator/replay viewer has per-element "First-Person …" HUD options and a separate "Game Mode Specific HUD" toggle. So the first-person hero HUD is a distinct layer, driven by "whose first-person view am I in". No public source documents the exact OW1 rules for spawn room, Assemble Your Team, kill cam or Practice Range HUD visibility.

### Cited Findings
- The Replay Viewer options menu (PTR 19 Nov 2020) lists: "Team 1/2 Banner", "Team 1/2 Heroes", "Status Messages", "Playback Indicators", "**Game Mode Specific HUD**", "Kill Feed", "Player Names", "Player Health Bars", "Player Outline Strength", "**First-Person Health**", "**First-Person Ultimate Meter**", "**First-Person Ability and Weapon Info**", "**First-Person Crosshair**", "**First-Person Hero HUD**", "**First-Person Activity Feed**", plus camera options — [PTR patch notes 19 Nov 2020](https://eu.forums.blizzard.com/en/overwatch/t/overwatch-ptr-patch-notes-%E2%80%93-november-19-2020/24881)
- A "Custom Spectator Options" menu for live spectating was added (retail 9 Mar 2021). It is opened with a "View Spectator Options Menu" button. The notes do not list the individual options — [Retail patch notes 9 Mar 2021](https://us.forums.blizzard.com/en/overwatch/t/overwatch-retail-patch-notes-%E2%80%93-march-9-2021/593440)
- The replay viewer offers first-person, third-person and free/top-down cameras. Spacebar toggles 1P/3P, F1–F12 follow specific players, and the UI can be hidden — [Blizzard: Introducing Overwatch Replays](https://overwatch.blizzard.com/it-it/news/23000187/introducing-overwatch-replays-see-your-past-games-from-new-perspectives/)
- Spectator HUD updates in 2019 put status effects in the top-left/right hero portraits, added a dynamic third-person camera and an option for hero-icon opacity — [BlizzardWatch](https://blizzardwatch.com/2019/01/07/overwatch-ptr-updates-spectator-mode-improves-visual-cues-easier-overwatch-league-viewing/)
- The beta emulator notes the "Press H to select Hero" prompt "always appears after spawning, because the server sets a flag in a component". It also says the player tablist "does not work" but "can be force-enabled in a Statescript script" — [Prometheus README](https://github.com/saturn-xvi/prometheus)

### Inferences
- The option names map onto the project's layer findings. "First-Person Hero HUD" likely corresponds to `HUD_<Hero>` (e.g. HUD_Tracer) and HUD_Hero_Common(_Animated). "First-Person Health / Ultimate Meter / Ability and Weapon Info / Crosshair" are probably sub-elements of HUD_Hero_Common. "Game Mode Specific HUD" ≈ HUD_Elements_Objectives (graph 0x106b). The client-setting names `Spectator_Show1PHeroHUD` and `Spectator_ShowGameModeHud` are almost certainly the backing settings for these menu entries.
- Practical consequence: in a spectator/replay context these settings gate the HUD. In normal play the HUD should not depend on them. If the client believes it is in a spectator/replay-like context (e.g. controller filter bits marked spectator, or the selected entity not recognised as the *local player*), the 1P hero HUD may be suppressed or routed through the `Spectator_Show1PHeroHUD` path. This is a candidate cause to rule out.
- From general OW1 play (not sourced; widely known gameplay behaviour, listed here as unverified): the hero HUD is visible in the spawn room during setup and in Practice Range. It is hidden during hero select, kill cam, Play of the Game/highlights and death spectate (which shows the spectated player's HUD only in some modes). Hence spawn-room/pre-match is probably *not* a HUD-hiding state, and the project's missing HUD after spawn is more likely a missing data/context than a game-phase gate.

### Gaps
- No primary source lists the live-spectator "Custom Spectator Options" names, or states exactly which phases hide the hero HUD in OW1 (kill cam, POTG, Assemble Your Team, overtime, round transitions).
- No source describes Practice Range/Training-specific HUD behaviour.

## 3. Workshop HUD actions and what they imply about engine HUD flags

### Takeaway
The Workshop (July 2020) exposes per-player boolean toggles for six HUD groups: Hero HUD, Game Mode HUD, Game Mode In-World UI, Kill Feed, Messages, Scoreboard, plus Nameplates. Each is "disabled until re-enabled". This strongly implies per-player, server-replicated HUD-visibility flags (or statescript variables) that are independent of hero state.

### Cited Findings
- New actions in the PTR of 15 July 2020: "Disable/Enable Game Mode HUD", "Disable/Enable Game Mode In-World UI", "Disable/Enable Hero HUD", "Disable Kill Feed"/"Enabled Kill Feed" (sic), "Disable/Enable Messages", "Disable/Enable Scoreboard", "Disable/Enable Nameplates". The same patch added "Set Ammo", "Set Max Ammo", "Set Weapon", "Set Reload Enabled", "Set Ability Charge", "Set Ability Resource", health-pool actions and "Set Player Health" — [PTR patch notes 15 Jul 2020](https://eu.forums.blizzard.com/en/overwatch/t/overwatch-ptr-patch-notes-%E2%80%93-july-15-2020/23790)
- "Disable Hero HUD": "Disables the Hero HUD for one or more Players until reenabled". Argument Player (Player or Array, default Event Player), returns Void — [workshop.codes: Disable Hero HUD](https://workshop.codes/wiki/articles/disable+hero+hud)
- "Disable Game Mode HUD": "Disables the Game Mode HUD for one or more Players until reenabled", with the same argument — [workshop.codes: Disable Game Mode HUD](https://workshop.codes/wiki/articles/disable+game+mode+hud)
- "Enable Hero HUD" undoes Disable Hero HUD — [workshop.codes: Enable Hero HUD](https://workshop.codes/wiki/articles/enable+hero+hud); the same holds for Game Mode HUD — [workshop.codes: Enable Game Mode HUD](https://www.workshop.codes/wiki/articles/enable+game+mode+hud)
- Create HUD Text gained "Sort Order Reevaluation Options" (Feb 2020), so custom HUD text is a server-driven, per-player reevaluated UI element — [PTR patch notes 4 Feb 2020](https://eu.forums.blizzard.com/en/overwatch/t/overwatch-ptr-patch-notes-%E2%80%93-february-4-2020/21568)

### Inferences
- Workshop actions are server-side scripts acting on player entities. A per-player "Disable Hero HUD" means the default is **enabled**, and the server only needs to replicate something when hiding it. If the HUD is enabled by default for a normal player, the project's missing HUD is probably not a missing "enable" flag. It is more likely a missing prerequisite context: the local player/controller identity, team/PlayerInfo, a game-mode "player is in game" state, or health/ability data the HUD binds to.
- These Workshop toggles were added in 2020 (build ≥ 1.47), so the final 104319 client contains them. In the client they are probably implemented as replicated booleans read by the HUD statescript (e.g. ConfigVars bound into the UX presenter's properties, like `ShowHeroHud`). A useful search is the reverse direction: find which synced/global statescript variable or component field feeds HUD_Root's `ShowHeroHud` binding, and check its default value.
- "Game Mode In-World UI" is separate from "Game Mode HUD". In-world icons (e.g. the cyan chevron seen in run 126) are therefore a different layer from the screen-space objective HUD.

### Gaps
- No public source maps Workshop actions to client data fields or statescript variables. Blizzard never documented the implementation.
- The exact list of elements hidden by "Disable Hero HUD" (health? crosshair? ult meter?) is not documented on workshop.codes. Whether the crosshair belongs to "Hero HUD" is unverified.

## 4. Datamining knowledge of UX/HUD assets (OWLib/TankLib)

### Takeaway
OWLib's generated STU types show that Overwatch's UI framework ("UX") is a WPF/XAML-style retained-mode system. It has DependencyObject, Binding/MultiBinding/PriorityBinding with PropertyPath, ViewModel, ContentPresenter/ItemsControl, VisualStateManager/Storyboards, ResourceDictionary, RoutedCommand and Screens. Statescript UX presenter states carry a condition, input/output event plugs, and a list of {identifier, ConfigVar} bound properties. UX screens are asset type 0x5A. The project's HUD layer GUIDs with prefix 0x09a0 decode to exactly that type.

### Inferences
- GUID type decoding: the project's rule "raw bits 48–59 = bitrev12(type−1)" checks out against known types (0x0790→0x9F MapHeader, 0x0230→0xC5 GameMode, 0x0240→0x25 GameMessage, 0x0a50→0xA6 SkinTheme). Applied to the HUD layer prefix 0x09a0 it gives type **0x5A = UXScreen**. HUD_Root, HUD_Tracer, HUD_Hero_Common and HUD_Elements_Objectives are therefore UXScreen assets. Other decodes:
  - 0x0d80 (UX plug ids) → 0x1C, likely STUIdentifier.
  - 0x0a40 (game-message parameter ids) → 0x26.
  - 0x0a88 → 0x116, not named in TankTonka. It could be a newer UX resource type; check before relying on it.
- The WPF-like design means a HUD screen is a tree of elements whose properties are **Bindings with PropertyPaths into a view-model/data context**. If a binding's source is missing, WPF-style systems use `m_fallbackValue` (often collapsed/hidden). A HUD screen whose data context (local hero, health component, ability data) is null could therefore load and run but render nothing. That matches the project's observation of running UX presenters with widgets created and nothing drawn.
- `STUUXScreen.m_sampleData` points at a structured-data "sample data" asset. This is probably design-time sample view-model data, so the shapes the HUD expects could be read from it offline: field names/hashes of health, ammo, abilities, and so on. `UXViewModelSchema` (0xB0) assets are the likely schema for those view models. Dumping the 0xB0 schemas referenced by HUD_Hero_Common / HUD_Root would show which data sources the hero HUD binds to: local player, hero entity, health component, weapon.
- UX presenter bound properties (`m_4FF3A882`: identifier + ConfigVar) are the statescript→UX bridge. On the project's HUD_Root presenter, `ShowHeroHud`/`ShowDistortion` are such pairs, so their ConfigVars (often Expression/Dynamic vars) decide visibility. Evaluating those ConfigVars on a live dump is a concrete next step. The `m_condition` on the presenter (STU_5F31962C) is a second gate. Both must be true, and neither is necessarily a networked flag.
- The polymorphic `m_45216F79` (STU_99CEEC04 with `m_priority`) likely encodes layer placement/priority (screen-stack/layer push). The HUD may require a parent root layer (HUD_Root) to be present before hero layers attach. The project already found HUD_Root creators (0x9cf9b0 / 0xafb740); the presenter-side layer field may name the parent.

### Gaps
- No public tool decodes UXScreen (0x5A) or UXViewModelSchema (0xB0) assets into readable trees. OWLib defines the STU types but has no "ExtractUX" mode; the TankTonka enum lists the types only. Offline decoding would need the project's own STU reader.
- The names of the hashed fields (m_4FF3A882, m_45216F79, …) are not public.

## 5. Player entity vs hero entity ownership of HUD (local player, controlled actor)

### Takeaway
The only public implementation evidence is the Prometheus beta (0.8) emulator. There the client has a separate **controller** entity, the "local player", carrying a LocalPlayer component (0x2F), a PlayerInfo component (0x3F) and FilterBits (0x10, team/spectator bits). The **hero model** entity carries health (0x28). The spawner sets PlayerInfo fields (slot 3, selected hero id, hero-selected flags) and team filter bits on the controller. The project has neither PlayerInfo nor health replicated, and these are the most plausible missing HUD data sources.

### Cited Findings (Prometheus beta source; project-vendored copy of the public upstream [saturn-xvi/prometheus](https://github.com/saturn-xvi/prometheus), files `prometheus/entity_admin.h`, `prometheus/player_spawner.cpp`, `prometheus/entity_admin.cpp`)
- README: "the local player is identified through component 2F (local player component) and component 20 (model reference component) on the controller entity". The default setup spawns Tracer; "Weapons don't appear". The player tablist does not work unless "force-enabled in a Statescript script"; icons/fonts need font files — [Prometheus README](https://github.com/saturn-xvi/prometheus)
- `Component_3F_PlayerInfo` is commented "Alles ist MirrorData" (all mirrored/replicated data). Fields at +0x20 offsets: `selected_heroid` (0x78), `unconformed_selected_heroid` (0x90, "when hero is not finally chosen yet"), `m_slot` (0xa0), `localplayer_heroselected` (0xa1), `hero_was_selected` (0xa2), `hero_select_enabled` (0xa3) — [entity_admin.h](https://github.com/saturn-xvi/prometheus) (struct Component_3F_PlayerInfo)
- The spawner sets `hero_select_enabled = true`, `hero_was_selected = true`, `m_slot = 3`, `selected_heroid = heroid`, `localplayer_heroselected = true` on PlayerInfo — [player_spawner.cpp](https://github.com/saturn-xvi/prometheus) (modify_ent)
- FilterBits (component 0x10, comment "Alle values vom ReplayController"): `set_team` writes team bits in mask 0x3C0000 (team 0 → 0x40000, team 1 → 0x80000, …). The spawner then sets `filter_bits = 0x800000` and calls `FilterBitsMakeFinal`. `set_filterbits_spectator` sets `pre_filter_bits = 0x400001` and other spectator markers — [entity_admin.h](https://github.com/saturn-xvi/prometheus)
- The local-player template uses controller resource 0x040000000000000E with `cam_attach`/`aim_attach`/`movement_attach` = model, `set_localent`, `load_3f`. The model (0x0400000000000001 Tracer) has `set_health` (component 0x28 STUHealthComponent part enabled, curr 169/max 200), `weapon_attach` and `fixup_player_statescript` — [player_spawner.cpp](https://github.com/saturn-xvi/prometheus)
- The beta hero-select handler `STUStatescriptStateUXHeroSelectScreen` (name hash 0x8F23FA30) compares `selected_heroid` on the local entity's PlayerInfo with the chosen hero before respawning — [entity_admin.cpp / STU.h](https://github.com/saturn-xvi/prometheus)

### Inferences (mapped to the project; hypotheses ranked)
1. **PlayerInfo/player-slot data is the strongest candidate gate.** HUD_Hero_Common (health, abilities, ult) almost certainly binds through "the local player's PlayerInfo → selected hero → hero entity" chain. In beta this was mirrored data on the controller, and the project has never replicated it. Action: find the retail equivalent of component 0x3F (beta id; the retail numbering differs). Look for a component on the controller with a hero GUID plus slot/hero-selected bytes. The retail comp 74 (with u64 hero GUID field 0, team field 2, spawn-room field 6) is the closest known analogue, but it may be a separate "player state" component. Then check whether `m_slot`/hero-selected/hero-select-enabled-style fields exist and are zero.
2. **Health replication.** The beta spawner explicitly enabled health part 0 on the model entity. The project's red vignette means the client sees no or zero health. A HUD health bar binding to a missing/disabled health part could make HUD_Hero_Common (or its "alive" visual state) stay collapsed. Replicating the hero's health component state (retail component carrying STUHealthComponent) is a prerequisite either way.
3. **Team and filter bits.** Beta set a team bit and 0x800000 in FilterBits and distinguished spectator filter bits. Workshop/spectator UX shows the client renders HUD differently for spectators. If the controller's filter bits are unset or spectator-like, the client may treat the view as non-player (or route through `Spectator_Show1PHeroHUD`). Replicate team/filter state for the controller and hero.
4. **Local-player identity vs "viewed entity".** The replay/kill-cam design (Orwig) and the spectator "First-Person Hero HUD" option imply the HUD takes a "view target" context. The project found AECBBA41 needs a world-owned UI context while the UI entity is root-owned. That fits a model where the in-game HUD's context is supplied by the *world* (the local player's controller in the live world), not by the global UI entity. Look for what attaches a world-owned UI context: likely native code reacting to the local player/controller becoming "ready" (PlayerInfo + selected hero), not a statescript create.
5. **Default-on Workshop toggles.** Hero HUD / Game Mode HUD are enabled by default (Workshop disables them explicitly), so do not search for an "enable HUD" message. Search for the binding sources and conditions described above.
